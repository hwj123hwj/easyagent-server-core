# 评审 001：受控操作能力的缺口

状态：原始评审已处理，设计采纳与修正见下文；尚无实现。原文保留作为历史讨论，不作为当前执行合同。
日期：2026-10-12。
针对版本：`e2874c1`（可嵌入核心取向的 RFC-001 / THREAT-MODEL / ACCEPTANCE）。

## 本轮采纳与修正（2026-10-12）

当前方案以 [RFC](RFC-001-SERVER-RUNTIME.md)、[威胁模型](THREAT-MODEL.md) 和 [验收计划](ACCEPTANCE.md) 为准。以下是本轮设计决定，不代表能力已经实现或宿主已获生产操作授权。

| 原始建议 | 本轮处理 |
| --- | --- |
| 保持无通用 shell/脚本/原始 SQL/任意 URL | 采纳；禁止用通用管理回调包装命令字符串绕过边界 |
| 允许具名受控业务操作 | 采纳；区分 read/write 与权限/审批，首个宿主仍先做查询和只读诊断 |
| 操作与读取可控性同一量级 | 不作为保证；写操作额外需要影响限制、业务去重、结果确认和审计 |
| 增加 Idempotent 声明 | 不以布尔标记证明幂等；默认不自动重试/重放写，稳定操作标识与真实去重由业务接口落实 |
| 增加审批通道 | 采纳可选宿主接口；每次都鉴权，需确认时缺少通道返回待批准，不能放行 |
| 写分支加在原查询链之后 | 修正；批准必须在实际副作用之前，执行前复核权限、预算与目标状态 |
| 表达部分成功 | 采纳 applied/conflict/partial/unknown 结果语义；超时或取消不证明未生效 |
| 通用变更配额/补偿/dry-run | 保留最小写调用预算和工具业务范围；不预建配额平台、补偿或干跑引擎 |

进一步收敛：公共核心仅保留模型、工具、有界循环、权限/可选审批与事件。历史会话、PG/Redis、持久任务、outbox、租约及多 worker 恢复交给宿主按需实现，不再作为核心的必需存储接口或固定后续版本。

原文关于任意命令“无法预算/审计”的论述不视为绝对技术结论：期限、进程控制和审计可以提供部分限制，但不自动获得所需的业务语义与资源边界。本项目排除通用执行的依据是范围和需求，不尝试证明任何命令沙箱都不可能安全。

原文引用的上游具体行号是针对评审时版本的观察，并非对当前全部上游入口的保证。来源实现需在实际提取代码时重新核对；本项目明确缺少有效批准时不得执行需确认的工具。

原 §8 的待确认项不阻塞最小核心：真实宿主暂不启用写；审批与影响额度在确有业务操作需求时，由宿主接入流程确定并验证。

## 0. 结论摘要

1. **砍掉「通用执行」是对的，不应改动。** shell、SSH、kubectl、任意文件编辑、原始 SQL、任意 URL 这类没有资源边界的能力，与本设计「每次调用可预先声明、鉴权、预算、审计」的前提结构性冲突，必须排除。
2. **但把「只读」当成核心定位，会连带砍掉「业务操作」**（重跑任务、改状态、发通知、标记工单、发布产物）。这是实际业务场景真实需要的能力，也是当前文档没有正面处理的一块。
3. **关键发现：现有工具协议本身是能力中立的。** `ToolCall` / `Observation` / `ToolExecutor`（RFC §4）不包含任何「只读」字样；排除操作能力是**策略选择**（体现在工具集合和正文表述里），不是**协议限制**。因此补上受控操作能力**不需要新范式、不需要新进程、不需要沙箱**，只需要把操作建模成具名工具并补齐若干合同字段。
4. 建议：保留「无通用执行」这一条不动，另补一章「具名受控操作」，把操作能力作为一等公民正式纳入协议；同时修订威胁模型 `THREAT-MODEL.md:38` 那一条的绝对表述。

## 1. 先分清三种「能力」

当前文档用「无命令工具」一刀切，实际上被讨论的是三种风险性质完全不同的东西：

| 类别 | 例子 | 资源边界 | 主要风险 | 本设计应有的处置 |
| --- | --- | --- | --- | --- |
| 一、读 | `schedule.inspect`、`job.runs`、`artifacts.inspect` | 有（白名单资源） | 泄密 | 已保留，正确 |
| 二、具名受控操作 | `job.retry`、`publication.republish`、`ticket.comment` | 有（具名工具 + 资源范围） | 误操作、越权、重复执行 | **当前缺失，本文主张补上** |
| 三、通用执行 | bash、任意文件编辑、任意 SQL、任意 URL | **无** | 可碰操作系统全部资源 | 应继续排除，本文不主张放开 |

文档现在的表述把二和三合并成「无执行能力」，是这次评审要拆开的核心。拆开之后：
- 类别三必须长期排除，理由见 §2；
- 类别二应当允许，且它的安全性完全可以通过「具名 + 范围 + 审批 + 幂等」达到与类别一同一量级的可控性。

## 2. 为什么类别三必须排除（结论不变）

依据现有文档自己的推理链：

- RFC §4 把执行链固定为 `schema 校验 → 预算/执行权校验 → Authorizer → Execute → 脱敏 → Evidence 登记`（`RFC-001-SERVER-RUNTIME.md:109`）。这条链要求**任何一次调用在发生前就能被声明、鉴权、计预算**。
- 类别三恰好击穿这条链的每一环：
  - **无法预先鉴权**：`sh -c "任意字符串"` 的 `Arguments` 是黑盒，鉴权器无法在调用前区分 `ls` 与 `rm -rf`。
  - **无法预先预算**：一条命令的耗时、字节、外部调用次数在调用前不可知，`Timeout`/`MaxResultBytes` 形同虚设。
  - **无法审计**：审计一条「执行了 bash」等价于没有信息，`Arguments` 本身即敏感且不可读。
  - **无法撤销**：`Run` 可取消，但已执行的删除不可回滚。
- 因此排除类别三是**结构性正确**，不是保守。K8s 应用安全清单的引用（RFC §12）也支持这一点。

**本文不主张为类别三做沙箱或放开。** 已确认该路线（沙箱 + 独立执行身份）不在本项目需求内。

## 3. 为什么类别二不应被一并砍掉

### 3.1 业务场景需要它

RFC §9 的示例任务（产物排查）目前止步于「输出最早阻塞点、证据和人工下一步建议」（`RFC-001-SERVER-RUNTIME.md:159`）。真实运维场景里，「人工下一步」往往就是那个 Agent 本该能安全执行的受控动作：重跑一次任务、重新发布一份产物、补一条工单备注。只能建议不能做，价值的落点就少了一截。

### 3.2 它与类别一的可控性是同一量级

类别二和类别一共享全部约束：具名（有 `Name`/`Version`/`InputSchema`）、有资源范围（不接受模型指定任意目标）、可在调用前鉴权、可预算、可审计、可要求审批。区别只是「改了状态」。正因为改了状态，才**更需要**纳入这套机制，而不是排除出去——排除出去的结果是这些操作留在宿主的管理页面里，由人手工点，而 Agent 拿不到。

### 3.3 当前文档里那一条绝对表述需要修订

`THREAT-MODEL.md:38`：

> 已有应用包含管理功能时，禁止把管理执行接口注册为助手工具；正常管理页面与助手查询是不同能力。

这一条应区分两种「管理接口」：

- **应保持禁止**：粗粒度管理入口（执行任意脚本、通用配置写入、容器/集群操作）——这些本质是类别三换了件衣服。
- **可以有条件开放**：有明确语义、有资源范围、可幂等、可审批的**单一业务操作**。

建议把该条改写为「禁止把**通用管理执行入口**注册为助手工具；受控的单一业务操作必须以具名工具形式注册，并满足 §4 的字段要求」。这样既守住边界，又不把类别二误杀。

### 3.4 「只读」这个词在协议层并不存在

这是本次评审最重要的判断，值得单列：

```go
type ToolCall struct { Name, Version string; Arguments json.RawMessage }
type Observation struct { EvidenceID, Status, Summary string }
type ToolExecutor interface { Execute(ctx, ExecutionContext, ToolCall) (Observation, error) }
```

以上（RFC §4，`RFC-001-SERVER-RUNTIME.md:82-100`）没有任何字段声明「只读」或「写」。一个 `job.retry` 和一个 `job.runs` 在类型上是同一形状。也就是说：

- 排除操作能力是**策略**（工具集合里不放、正文里写「不提供」），不是**协议强制**；
- 所以放开类别二**不需要改架构**，只需要（a）注册具名操作工具，（b）补齐 §4 列出的字段缺口。

## 4. 受控操作需要的合同缺口

现有 `Observation` 与预算模型是**读形状**的，直接套用到写操作会留下真实风险。以下按优先级列出必须补的字段/合同：

**P1 · 幂等与去重（最高优先级）**

RFC §7 承认「飞行中的读取可能重复」（`RFC-001-SERVER-RUNTIME.md:143`），对读可以接受。**对写不可接受**：一次重复的 `job.retry` 就是一次生产事故。现有幂等键挂在 **Run 层**（`RFC-001-SERVER-RUNTIME.md:137` 的 RunStore 字段，并在 `:141` 用于多 worker 防重复提交），而重试/接管会在**工具调用层**重放步骤。因此需要：

- `ToolSpec` 增加 `Idempotent bool` 或 `IdempotencyKeyFrom []string`（如何从参数派生去重键）；
- 或明确：非幂等操作在恢复/重试路径上**不得自动重放**，必须降级为 `interrupted` 并提示人工确认。

**P1 · 审批通道**

高风险操作在无人批准时不得执行。当前 easyagent 的 confirm 回调仅在交互式入口注入，serve/feishu 留空即放行（`sdk/runtime/agent_session.go:619-620`），这意味着「服务端无人值守」这条路径上没有任何审批落点。RFC 需要一个明确的设计位：

- `ToolSpec` 增加 `RequiresApproval`（或风险等级）；
- Chat/Agent 遇到需审批操作时的语义：挂起、返回「待批准」公开事件、由宿主 UI 批准后续跑——而不是默认放行或直接失败。

**P1 · 变更结果的可审计表达**

`Observation` 现有 `EvidenceID/Status/Summary` 表达不了「我改了什么」。写操作需要：

- 结果中带**受影响资源标识**与**变更前后摘要**（供审计，不进入模型上下文的部分另行存放）；
- `Status` 枚举是读形状的（`available/missing/denied/unavailable/invalid`），写需要补 `applied` / `conflict` / `partial` 这类状态，且**部分成功必须显式表达**，不能折叠成成功或失败。

**P2 · 预算模型补充「变更配额」**

现有预算是轮数/工具次数/字节/token（`RFC-001-SERVER-RUNTIME.md:117-119`），都是读形状。写操作需要额外的**爆炸半径**限制：

- 单次 Run / 单账户 / 单 tenant 允许的**变更次数上限**；
- 单次调用允许影响的**资源数量上限**（例如一次最多重跑 1 个任务，不能批量 1000 个）。

**P2 · 撤销/补偿的表达位**

不承诺真回滚（很多外部系统做不到），但协议层应留有位置：

- `ToolSpec` 可选 `CompensatingAction string`，或至少在结果中声明「本次变更不可自动撤销」；
- 让「不可逆」成为显式元数据，而不是隐含假设。

**P2 · 干跑（dry-run）**

对受影响面较大的操作，提供 `dry-run` 语义（返回「将会发生什么」而不实际执行），可作为审批流程的默认前置。非必须，但成本低、收益明确。

## 5. 建议的最小增量

不改定位、不加沙箱、不加新进程，改动集中在协议与文档：

1. **协议（RFC §4）**：在 `ToolSpec` 上增加 `Idempotent`、`RequiresApproval`、`MaxAffectedResources`；在 `Observation` 上增加变更结果字段与写形状 `Status` 值；在 `ToolExecutor` 合同里明确「非幂等操作不自动重放」。
2. **执行链（RFC §4）**：在 `schema → 预算/执行权 → 授权 → 查询 → 脱敏 → 证据` 之后，为写操作增加 `审批（如需要）→ 执行 → 变更登记（审计）` 分支；读路径完全不变。
3. **威胁模型**：修订 `THREAT-MODEL.md:38`（区分通用管理入口与受控单一操作），并新增一行场景「模型提出受控写操作」，强制措施为「具名 + 范围校验 + 审批 + 幂等 + 变更审计」。
4. **验收（ACCEPTANCE.md）**：在「工具」行补充写操作用例——重复提交同一操作只生效一次；未批准的写操作被拒绝/挂起；部分成功的变更如实报告；越出资源范围的写操作被拒绝。
5. **示例（RFC §9 / ACCEPTANCE §demo）**：给虚构示例增加一个受控写操作（如 `job.retry` 的重跑场景），证明「诊断 → 建议 → 受控执行 → 验证」这条完整闭环，同时证明它不等同于通用执行。

## 6. 明确不做

- 不为类别三（通用执行）设计沙箱、独立执行身份或容器逃逸防护。已确认该路线不在需求内；若将来出现「必须让模型跑任意命令」的诉求，那应作为**独立课题**重新评估，不并入本项目。
- 不放开粗粒度管理入口（通用脚本、集群操作、任意配置写入）。
- 不让「操作能力」成为绕过授权/预算/审计的通道——类别二必须与类别一走同一条执行链。

## 8. 待确认
